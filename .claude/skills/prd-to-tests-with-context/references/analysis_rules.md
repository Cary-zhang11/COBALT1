# 关联分析规则

## 一、变更分析规则

### 适用条件

同时提供了**新 PRD/新用例**和**老需求文档**时执行。

### 分析步骤

**Step 1: 功能模块对齐**

建立新老需求的功能模块对照表：

```
新需求模块              老需求模块              关系
─────────────────────────────────────────────────────────
1.1 头图区域            1.1 头图区域            继承
1.2 卖点区域            1.2 卖点区域            继承+修改
1.3 留资区域            1.3 留资区域            继承
1.4 营销弹层            （无）                  新增
（无）                  1.4 推荐车源            删除
```

**Step 2: 规则差异提取**

对对齐后的每个模块，逐条对比规则描述：

- **文案变更**：同一功能的不同文字描述。例：老"立即卖车"→新"我要卖车"
- **规则变更**：条件判断/计算逻辑变化。例：老">3项标红"→新">=3项标红"
- **流程变更**：操作步骤/校验顺序变化。例：老"协议→城市"→新"城市→协议"
- **参数变更**：字段名/枚举值/阈值变化。例：老"pvareaid=429"→新"pvareaid=430"
- **交互变更**：用户操作方式变化。例：老"点击跳转"→新"弹层内完成"
- **范围变更**：功能适用场景增减。例：老"仅APP"→新"APP+H5"

**Step 3: 影响评估**

每条差异标注影响程度：

- **高**：涉及核心流程、主入口、关键计算 → 必须补充用例验证
- **中**：涉及次要功能、展示逻辑、边界规则 → 建议补充用例
- **低**：纯文案、样式、无功能影响的调整 → 标记即可，不强制补用例

**Step 4: 未提及功能判断**

老需求中有、新需求未提及的功能，判断逻辑：

```
老需求功能A在新需求中未提及：
  ├─ 新需求其他章节明确替代了功能A → 已删除
  ├─ 功能A属于核心能力，新需求应继承 → 可能遗漏，记入待澄清
  └─ 功能A是独立模块，新需求聚焦其他模块 → 可能不涉及本次迭代
```

## 二、用例复用分析规则

### 适用条件

提供了**历史测试用例**时执行。

### 分析步骤

**Step 1: 功能模块映射**

将历史用例按功能模块归类，与新用例的模块结构对齐：

```
历史用例模块          新用例模块            映射关系
─────────────────────────────────────────────────────
2.1 头图区域          1.1 头图区域          一对一
2.2 卖点区域          1.2 卖点区域          一对一
2.3 留资-手机号       1.3.2 手机号校验       一对多（子模块拆分）
2.4 营销弹层          （无）                无映射（历史独有）
```

**Step 2: 用例级别对比**

对映射成功的模块，逐条对比历史用例和新用例：

**对比维度：**

- **测试场景**
  - 完全相同：同一用户操作路径
  - 部分不同：类似但条件/参数不同
  - 完全不同：完全不同的操作
- **前置条件**
  - 完全相同：环境/状态一致
  - 部分不同：条件类似但参数不同
  - 完全不同：完全不同的前提
- **测试动作**
  - 完全相同：操作步骤一致
  - 部分不同：操作类似但顺序/入口不同
  - 完全不同：完全不同的动作
- **预期结果**
  - 完全相同：校验点一致
  - 部分不同：部分校验点变化
  - 完全不同：完全不同的预期

**判定规则：**

```
场景相同 + 动作相同 + 预期相同 → 完全复用
场景相同 + (动作不同 或 预期不同) → 部分复用（需适配）
场景不同 → 不相关（历史独有或新需求独有）
```

**Step 3: 遗漏识别**

检查历史用例中存在的测试维度，新用例是否覆盖：

- **异常场景缺失**：历史用例有"为空/错误/超时"类用例，新用例无 → 补充异常用例
- **边界条件缺失**：历史用例涉及具体边界值，新用例无 → 补充边界用例
- **状态组合缺失**：历史用例覆盖了多种状态组合，新用例仅覆盖主状态 → 补充分支用例
- **权限场景缺失**：历史用例有登录态/权限差异用例，新用例无 → 补充权限用例
- **逆向操作缺失**：历史用例有"取消/关闭/返回"类用例，新用例无 → 补充逆向用例

## 三、Bug 回归分析规则

### 适用条件

提供了 **Bug 记录（Excel/CSV）** 时执行。

### Bug 字段提取

从 Bug 记录中提取以下关键字段：

- **Bug 标题**：问题简述 → 判断功能模块和影响范围
- **功能模块**：Bug 所属的模块 → 与新用例模块对齐
- **严重级别**：P0/P1/P2/P3 → 决定回归用例的优先级
- **复现步骤**：触发 Bug 的操作路径 → 生成回归用例的前置条件+动作
- **实际结果**：Bug 现象 → 反转为预期正确结果
- **预期结果（Bug方）**：修复后应有的表现 → 直接作为回归用例预期
- **根因分析**：技术根因 → 判断是否涉及同类场景
- **修复版本**：哪个版本修复 → 判断是否在本次迭代范围内
- **重复出现**：是否重复打开 → 重复出现必须生成回归用例

### 回归用例生成规则

**Step 1: 筛选高价值 Bug**

满足以下任一条件即生成回归用例：

1. 严重级别为 P0/P1
2. 根因涉及边界条件、异常处理、并发、数据一致性
3. 3 个月内重复出现 2 次及以上
4. 修复方案涉及代码逻辑变更（非配置/文案修改）
5. 涉及核心业务流程

**Step 2: 功能模块存在性检查**

```
Bug 涉及的功能模块：
  ├─ 新需求中仍然存在该模块 → 生成回归用例
  ├─ 新需求中已删除该模块 → 记录但不生成（模块已移除）
  └─ 新需求中该模块已完全重构 → 分析重构后的等效场景，决定是否生成
```

**Step 3: 用例生成**

回归用例格式：

```
- tc-{编号}-p{优先级}：回归验证-{Bug单号}-{核心场景}
  - {复现环境}，{触发Bug的操作路径}【历史Bug补充】
    - {验证修复后的正确行为1}
    - {验证修复后的正确行为2}
    - 不出现历史Bug现象：{Bug现象描述的反述}
```

**编写要点：**
- 前置条件尽量复用 Bug 报告中的复现环境
- 测试动作与 Bug 复现步骤一致（验证修复后不再复现）
- 预期结果必须包含"正确行为" + "不出现历史 Bug"双重验证
- 如果 Bug 修复方案有明确的技术方案，预期结果应能验证该方案生效

**示例：**

Bug：输入手机号为空时提交，未自动带入登录手机号，导致提交失败。

回归用例：
```
- tc-130-p1：回归验证-BUG-2024-0015-手机号为空自动带入
  - 未填写手机号，点击提交按钮【历史Bug补充】
    - 系统自动带入登录态手机号
    - 发送验证码成功
    - 不出现：提交失败或提示手机号为空
```

## 四、维度覆盖分析规则

### 适用条件

提供了**历史测试用例**时执行（可与用例复用分析同时进行）。

### 分析矩阵

对每个功能模块，建立新/旧用例的维度覆盖对比：

```
模块：头图区域
────────────────────────────────────────
维度            历史用例    新用例    状态
────────────────────────────────────────
主流程(D1)        3个        3个      持平
分支流程(D2)      2个        1个      不足
异常容错(D3)      4个        2个      不足
边界条件(D4)      2个        0个      缺失
权限安全(D5)      1个        0个      缺失
兼容性(D6)        2个        1个      不足
────────────────────────────────────────
```

### 补充策略

- **缺失**：历史有、新用例完全无该维度 → 按该维度生成补充用例
- **不足**：新用例有但该维度数量<历史的50% → 分析原因，补充核心场景
- **持平**：数量相当 → 不处理
- **新增**：新用例有、历史无（新功能特有） → 不处理

**注意**：维度覆盖分析用于发现"系统性遗漏"，而非简单追求数量一致。如果新需求确实简化了该模块（如删除了复杂配置），维度减少是合理的，此时应标注"合理减少"而非"不足"。

## 五、分析结果输出格式

### 中间产物：分析摘要

在生成最终用例前，先输出分析摘要供用户确认：

```markdown
## 关联分析摘要

### 1. 资料来源
- 新用例：{文件路径}，共 X 个模块，Y 条用例
- 老需求：{文件路径}，共 A 个模块
- 历史用例：{文件路径}，共 B 条用例
- Bug 记录：{文件路径}，共 C 条记录

### 2. 变更分析（如有老需求）
- 新增模块：X 个
- 删除模块：X 个
- 修改模块：X 个
- 未提及功能：X 个（其中 X 个记入待澄清）

### 3. 用例复用分析（如有历史用例）
- 完全复用：X 条
- 部分复用：X 条
- 应废弃：X 条
- 待补充：X 条

### 4. Bug 回归分析（如有 Bug 记录）
- 高价值 Bug：X 条
- 涉及模块仍存在：X 条
- 生成回归用例：X 条

### 5. 维度覆盖分析（如有历史用例）
- 维度缺失模块：X 个
- 维度不足模块：X 个
- 建议补充用例数：X 条

### 6. 预计补充用例总数
- 需求变更补充：X 条
- 历史用例补充：X 条
- 历史Bug补充：X 条
- 维度覆盖补充：X 条
- 合计：X 条
```

用户确认后，再执行 Step 3（用例补充）和 Step 4（输出文档）。
