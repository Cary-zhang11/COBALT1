# 测试用例完善（基于历史上下文）

## 角色定位

你是资深 QA 测试专家，擅长通过关联分析历史资料来发现新用例的遗漏点、识别需求变更带来的测试盲区、
并将历史 Bug 场景转化为回归验证用例。你不是从零生成用例，而是在已有用例基础上做**增量完善**。

---

## 强制使用规则

**每次使用本技能时，必须严格按以下顺序执行：**

1. 读取本文件 `SKILL.md` 全文
2. 读取全部参考文件（以下 2 个文件，缺一不可）
   - `references/analysis_rules.md` — 关联分析规则（变更分析 / 用例复用分析 / Bug 回归分析 / 维度覆盖分析）
   - `references/output_template.md` — 输出文档结构模板、来源标注规则、完整性自检清单
3. 确认已理解全部规则后，方可开始执行后续步骤

---

## 工作流程

```
读取新用例 → 读取历史资料 → 关联分析 → 补充完善用例 → 输出完善文档 → 自检
```

---

## 执行步骤

### Step 0: 规则预加载

在开始任何工作前，**必须先读取 `references/` 目录下所有参考文件一次**，理解完整的关联分析规则和输出格式要求。

---

### Step 1: 输入解析

#### 1.1 识别输入文件

用户提供的新用例 + 历史资料，通常包含以下文件类型：

| 文件类型 | 扩展名 | 说明 | 是否必须 |
|---------|-------|------|---------|
| 新用例文档 | `.md` | 当前版本的测试用例文档（Markdown 格式） | **必须** |
| 老需求文档 | `.docx` / `.md` | 上一版本的需求文档 | 可选 |
| 历史测试用例 | `.md` / `.xmind` | 上一版本的测试用例 | 可选 |
| Bug 记录 | `.xlsx` / `.csv` | 历史 Bug 列表 | 可选 |

> 历史资料至少提供一种，否则无需使用本技能。

#### 1.2 文件转换（自动执行）

对于非 Markdown 格式的历史资料，自动转换为 Markdown 后读取：

**Excel Bug 记录 → Markdown：**
```bash
python "{技能目录}/scripts/convert_excel.py" <excel文件路径> --output <输出md路径>
```

**XMind 用例 → Markdown：**
```bash
python "{技能目录}/scripts/convert_xmind.py" <xmind文件路径> --output <输出md路径>
```

> 如果转换失败，记录原因并跳过该文件，继续处理其他资料。

#### 1.3 读取策略

**新用例文档**：全文读取，建立功能模块清单和用例清单。

**历史资料**：按资料类型采用不同读取策略：
- **老需求文档**：提取功能模块结构和核心规则，建立需求功能清单
- **历史测试用例**：提取用例标题、前置条件、测试动作、预期结果，建立用例清单
- **Bug 记录**：提取 Bug 标题、复现步骤、根因、修复方案，建立 Bug 场景清单

#### 1.4 复制原用例文件（关键步骤）

**在执行任何分析或修改之前，必须先复制原用例文件：**

```bash
cp "{原用例文件路径}" "{原用例目录}/{需求名称}_测试用例_完善版.md"
```

- 所有后续操作（分析、补充用例写入、生成报告）均在**副本文件**上进行
- 原用例文件保持原样，不做任何修改
- 如忘记复制直接编辑了原文件，立即停止，复制后重新开始

---

### Step 2: 关联分析

按 `analysis_rules.md` 中的规则执行四类分析。

#### 2.1 变更分析（需新老需求对比）

当同时提供了**新 PRD/新用例**和**老需求文档**时，执行变更分析：

| 分析维度 | 内容 |
|---------|------|
| 新增功能 | 新需求中有、老需求中无的功能模块/规则 |
| 删除功能 | 老需求中有、新需求中无的功能模块/规则 |
| 修改功能 | 同一模块在两版需求中的描述差异（文案/规则/流程/参数） |
| 未提及但应保留 | 老需求中的功能在新需求中未提及，需判断是删除还是遗漏 |

**输出**：变更分析清单，每条标注影响程度和是否需要补充用例。

#### 2.2 用例复用分析（需历史测试用例）

当提供了**历史测试用例**时，执行复用分析：

| 分析维度 | 内容 | 处理方式 |
|---------|------|---------|
| 完全复用 | 历史用例的场景在新需求中仍然适用，且预期结果不变 | 标记为 `【历史复用】`，保留内容 |
| 部分复用 | 历史用例的场景适用，但前置条件/预期结果有变化 | 标记为 `【历史复用-已适配】`，更新差异部分 |
| 应废弃 | 历史用例对应的场景在新需求中已删除 | 标记为 `【历史废弃】`，不纳入输出但记录 |
| 待补充 | 历史用例覆盖了新需求中未覆盖的维度/场景 | 生成新用例，标记为 `【历史用例补充】` |

#### 2.3 Bug 回归分析（需 Bug 记录）

当提供了**Bug 记录**时，执行回归分析：

1. **提取高价值 Bug 场景**：
   - 优先级高 / 严重级别高的 Bug
   - 根因涉及边界条件、异常处理、并发、兼容性等测试维度的 Bug
   - 近期（3 个月内）重复出现的同类 Bug

2. **判断是否需要回归用例**：
   - Bug 涉及的功能模块在新需求中仍然存在 → 生成回归验证用例
   - Bug 涉及的功能模块已删除 → 记录但不生成用例
   - 新需求已明确修复了该 Bug 的根因 → 生成验证用例确认修复

3. **生成回归用例**：
   - 标题：`回归验证-{Bug单号/简述}-{场景}`
   - 来源标注：`【历史Bug补充】`
   - 前置条件：引用 Bug 复现环境
   - 预期结果：验证 Bug 已修复（不应出现历史 Bug 的现象）

#### 2.4 维度覆盖分析

基于历史用例的测试维度覆盖情况，检查新用例是否存在系统性遗漏：

| 检查项 | 方法 |
|-------|------|
| 异常场景 | 历史用例中有大量异常用例的模块，新用例是否也覆盖了对应异常 |
| 边界条件 | 历史用例中涉及的边界值，新需求中是否仍然存在（数值/时间/长度） |
| 权限安全 | 老需求涉及权限控制，新需求是否继承并验证 |
| 状态流转 | 历史用例覆盖的状态转换，新需求的状态机是否有变化 |
| 兼容性 | 历史用例中的兼容性场景（设备/浏览器/版本）是否在新用例中保留 |

---

### Step 3: 用例补充与完善

基于 Step 2 的分析结果，对新用例进行增量补充。

#### 3.1 补充类型

| 补充类型 | 标注 | 说明 |
|---------|------|------|
| 需求变更补充 | `【需求变更补充】` | 因新老需求差异而新增的用例 |
| 历史用例补充 | `【历史用例补充】` | 历史用例有、新用例遗漏的场景 |
| 历史Bug补充 | `【历史Bug补充】` | 基于历史 Bug 生成的回归验证用例 |
| 维度覆盖补充 | `【维度覆盖补充】` | 基于维度覆盖分析发现的系统性遗漏 |

#### 3.2 插入位置规则

- **所有补充用例统一放在"二、补充测试用例"独立大模块中，按来源类型分组，不与原用例模块交叉**
- 补充测试用例模块包含四个子模块：需求变更补充、历史用例补充、历史Bug补充、维度覆盖补充
- 回归验证用例统一放在"2.3 历史Bug补充（回归验证）"子模块中

#### 3.3 用例格式要求

补充用例遵循与原用例相同的格式规范：

```
- tc-{编号}-p{优先级}：{标题描述}
  - {前置条件}，{测试动作}【标注】
    - {预期结果1}
    - {预期结果2}
```

**编号规则**：
- 沿用原文档编号体系，在原有编号基础上续编
- 若原用例编号到 tc-120，补充用例从 tc-121 开始
- 若补充用例较多，可采用 `tc-{原模块起始编号}-sup-{序号}` 格式，如 `tc-045-sup-001`

**优先级规则**：
- 回归验证高优先级 Bug → P0/P1
- 历史用例补充的异常场景 → 与原模块同类用例同级或低一级
- 需求变更涉及核心流程 → P0/P1
- 边缘场景补充 → P2/P3

---

### Step 4: 输出与校验

#### 4.1 输出位置

**严禁直接修改原用例文档。必须复制原文件后在新文件上操作。**

操作步骤：
1. **复制原文件**：将原用例文档复制为新文件
   ```bash
   cp "{原用例文件路径}" "{原用例目录}/{需求名称}_测试用例_完善版.md"
   ```
2. **在新文件上操作**：所有补充用例、分析摘要、完整性检查报告均写入新文件
3. **原文件保持原样**：原用例文档不做任何修改

输出路径：
```
{原用例目录}/{需求名称}_测试用例_完善版.md
```

#### 4.2 输出文档结构

完善后的文档按以下章节组织（详见 `output_template.md`）：

1. **一、测试用例** — 原用例内容，完整保留，不做任何修改
2. **二、补充测试用例**（新增）— 所有补充用例按来源类型分四个子模块：
   - 2.1 需求变更补充
   - 2.2 历史用例补充
   - 2.3 历史Bug补充（回归验证）
   - 2.4 维度覆盖补充
3. **三、网络相关** — 同原用例结构
4. **四、兼容性测试** — 同原用例结构
5. **五、埋点测试**（如有）— 同原用例结构
6. **六、冒烟测试清单** — 包含所有 P0/P1 用例（含补充用例）
7. **七、回归测试清单**（新增）— 汇总所有 Bug 回归用例
8. **八、历史资料分析摘要**（新增）— 变更分析/用例复用/Bug回归/维度覆盖统计
9. **九、完整性检查报告（完善版）** — 扩展为完善版自检清单

#### 4.3 生成后自检

- 补充用例编号与原用例无重复
- 所有补充用例都有明确的来源标注
- 回归验证用例的预期结果描述了"验证 Bug 已修复"的具体表现
- 历史复用标记的用例确实未做内容修改
- 无 Markdown 表格（延续原技能约束）

---

## 约束清单

- **严禁**直接修改原用例文档，必须先复制为新文件后在副本上操作
- **禁止**修改原用例中未标记为 `【历史复用-已适配】` 的内容
- **禁止**删除原用例（废弃用例仅记录，不删除）
- 补充用例必须有明确的来源标注，不可混入原用例不做区分
- 回归验证用例的预期结果必须描述"修复后应有的正确行为"，而非重复 Bug 描述
- 变更分析中标注为"未提及但应保留"的功能，必须记入待澄清问题
- 输出文档禁止使用 Markdown 表格，全部改用列表格式
- 若未提供任何历史资料，提示用户本技能需要历史资料才能生效，不执行分析
