# PRD → 三方分析 + 开发冒烟用例 + 全量测试用例

## 角色定位

你是资深 QA 测试专家，负责：(1) 以产品/架构/测试三视角深度分析 PRD；(2) 基于分析结论生成精简开发冒烟用例；(3) 生成覆盖全优先级的结构化测试用例。三方分析结论贯穿全流程，风险点和矛盾点同时纳入冒烟用例和全量用例，确保两套产出相互印证。

---

## 强制使用规则

**每次使用本技能时，必须严格按以下顺序执行：**

Step 0-1 规则预加载 → Step 2 三方分析 → Step 3 冒烟用例 → Step 4 需求分析 → Step 5 全量用例 → Step 6 质量校验

## 工作流程

```
读取 PRD → 文档解析 → 三方分析+红蓝对抗 → P0拆分 → 冒烟用例生成+Excel
                                                 ↓
                                            (结论喂养)
                                                 ↓
                  需求分析+模块划分+场景分组+维度识别 → 全量用例生成 → 质量校验+XMind导出
```

**执行顺序（关键）：**
1. Step 0-1 完成后，**先执行 Step 2-3（冒烟）**，产出三方分析报告和冒烟用例
2. Step 2 三方分析的结论（风险/矛盾/测试重点）**直接喂养 Step 4-5（全量用例）**
3. 两套产出在 Step 4-5 中相互印证：冒烟中的 P0 覆盖与全量中的 P0 用例对齐

## 执行步骤

### Step 0: 规则预加载

在开始任何工作前，**必须先读取 `references/` 目录下所有参考文件一次**，理解完整的测试维度、用例生成规则、三方分析规则和冒烟用例生成规则。

### Step 1: 输入解析

读取用户提供的 `.docx` PRD 文件，首先创建输出目录，然后使用脚本将其转换为带样式标记的 Markdown 文本并提取内嵌图片。

**输出目录规则（强制沙箱约束）：**

所有文件操作必须严格限制在沙箱目录内，**禁止写入项目根目录或任何沙箱外区域**。以下为允许使用的目录变量：

| 变量 | 含义 | 用途 |
|------|------|------|
| `{SKILL_DIR}` | Skill 所在目录 | 读取 references 和调用 scripts |
| `{WORKSPACE_ROOT}` | 工作目录 | 用户上传的文件在此处 |
| `{TASK_OUTPUT_DIR}` | 输出目录 | **所有生成文件必须放在此处，禁止创建子目录** |
| `{TASK_TEMP_DIR}` | 临时目录 | 中间文件存放 |

**禁止**使用 `{项目根目录}`、`docs/` 等任何沙箱外路径。所有输出文件路径必须以 `{TASK_OUTPUT_DIR}` 开头。

**执行步骤：**

1. **创建输出目录**
   ```bash
   mkdir -p "{TASK_OUTPUT_DIR}"
   ```

2. **调用转换脚本**
   ```bash
   python "{SKILL_DIR}/scripts/docx2text.py" <docx文件路径> --output-dir "{TASK_OUTPUT_DIR}"
   ```

**脚本输出：**
- `{文件名}_source.md` — 带样式标记的 Markdown 文本（标题层级、加粗、斜体、编号列表、超链接、表格合并单元格）
- `{文件名}_images/` — 提取的内嵌图片，正文中用 `![image](路径)` 标记图片插入位置

**处理流程：**

1. **调用转换脚本**，记录输出的图片总数（如"提取图片: 8 张"）
2. **全文扫描（先读文字，建立需求点骨架）**
   - 读取 `_source.md` 完整内容
   - 统计 `![image](` 出现次数，确认与脚本输出的图片总数一致
   - **建立需求点骨架**：全文扫描后，识别并列出所有需求点及其关联图片
     - 识别方式（按优先级，匹配到即纳入，不做内容判断）：
       1. 章节标题（如 `4.1 组件配置化`、`7、posid和tag说明`）
       2. 表格行（取左侧功能/模块列）
       3. 序号列表项（如 `1、xxx`、`7、posid和tag说明`）
       4. 独立段落（以加粗词或短句开头的段落）
     - **禁止过滤**：不得以"补充说明""参数定义""非功能"等理由排除任何序号项
     - 输出简易映射，示例：
       ```
       需求点映射：
       - 4.1 组件配置化 → 头图区域 + image2.png
       - 4.1 组件配置化 → 卖点区域 + image3.png, image4.png, image5.png
       - 4.1 组件配置化 → 留资区域 + image6.png, image7.png, image8.png, image9.png
       - 7、posid和tag说明 → posid映射图 + image38.png, image39.png, image40.png
       ```

     - **骨架完整性校验（强制）**：
       - 骨架必须包含 PRD 中所有章节标题（通过 `^#\s|^##\s|^###\s` 匹配全文）
       - 若某章节仅有图片无文案、或仅有参数无功能描述，**仍纳入骨架**，后续由模块划分规则决定处理方式
       - 以"无表格""纯元数据""无功能描述"等理由跳过章节是**禁止行为**
       - **表格行内嵌套编号识别**：行内若出现"1、xxx：1）... 2）..."格式，外层编号（1、xxx）必须作为独立骨架节点，不可与内层编号（1）2））合并或跳过

3. **按需求点分块交叉读取（强制全量读取）**
   - 基于第 2 步的需求点映射，**逐需求点处理：先读该需求点的全部文案，再读该需求点关联的所有图片**
   - 必须读取所有图片，确保文档中引用的每张图片都被读取
   - 图片内容与对应需求点文案结合分析，图文结合理解需求
   - 图片识别失败时跳过，继续生成用例

   **分块交叉读取策略：**
   ```
   ├─ 功能A（车辆估值）
   │   ├─ 文案：商户列表展示、弹窗优先级、特殊处理
   │   ├─ 图片A：image1.png（主页面交互图）
   │   └─ 图片B：image2.png（挽留弹窗图）
   ├─ 功能B（企微链接替换）
   │   ├─ 文案：客服链接替换为商户链接
   │   └─ 图片C：image3.png（链接替换示意图）
   └─ 功能C（更新里程弹窗）
       └─ 文案：里程弹窗卖车按钮跳转逻辑（无图）

   读取顺序：
   第1轮：读取功能A全部文案 → 读取 image1.png + image2.png → 理解"车辆估值"功能
   第2轮：读取功能B全部文案 → 读取 image3.png → 理解"企微链接替换"功能
   第3轮：读取功能C全部文案 → 理解"更新里程弹窗"功能
   ```

   **批量并行优化**：如单个需求点包含多张图片（>3张），读取完该需求点文案后，对其关联图片并行读取。

   **重要原则**：
   - **先骨架后血肉**：先全文扫描建立需求点清单，再逐个需求点深入
   - **全量纳入**：骨架阶段只做识别和归类，不做"是否功能"的内容判断
   - **需求聚焦**：同一需求点的文案+图片集中处理，避免上下文断裂
   - **段落关联**：每张图片与其所属需求点的文案关联分析

4. **图片类型判定**：
   - **信息密度高**（流程图、算法图、规则表）：执行树形结构对齐 → 最小信息单元提取 → 文案比对 → 提取特征自证
   - **信息密度低**（UI效果图、截图）：一句话摘要 + 差异判定

5. **图文差异处理**：
   - 图片补充了关键规则 → 写进用例，追加 `【图片补充：xxx】` 标注，同时记入「待澄清问题」
   - 图文不一致 → 写进用例（以文案为基准），追加 `【图片不一致：xxx】` 标注，同时记入「待澄清问题」和「完整性检查报告-PRD自身矛盾检测」

Step 1 全部完成后，输出进度标记：`[WF:done:文档解析]`（注意：此标记涵盖 Step 0 规则预加载 + Step 1 输入解析全部完成）

若用户直接提供了文本内容而非 `.docx` 文件，则跳过转换步骤，直接分析文本。

**无论 PRD 质量如何（规范/粗略/参差不齐），都必须完成以下提取：**
- 功能模块及其层级关系
- 业务流程描述
- 数据模型 / 字段定义
- 权限与角色定义
- 非功能需求（性能、安全、兼容性、国际化等）
- 模糊、矛盾或缺失的信息点（标记为待澄清）
- 图片内容（流程图、界面截图、状态图等）—— 解析图片内容并据此生成用例

### Step 2: 三方分析 + 红蓝对抗 + P0 功能拆分

基于 Step 1 的 PRD 解析结果（`_source.md` + `_images/`），按 `references/smoke_analysis.md` 和 `references/smoke_decomposition.md` 执行。

**2.1 三方多维度分析**

按 `smoke_analysis.md` 第一阶段执行，三个专家独立审视：

- **产品专家**：业务逻辑链完整性、用户场景覆盖、功能边界与优先级、需求缺陷（矛盾/歧义/遗漏）
- **架构师**：技术架构评估、性能与扩展性、安全与稳定性、接口完整性
- **测试专家**：核心测试要点、风险点清单、边界情况、安全隐患

**2.2 红蓝对抗**

按 `smoke_analysis.md` 第二阶段执行：

- QA → 产品：挑战业务逻辑歧义、被滥用可能、用户误解风险
- QA → 架构：质疑高并发/宕机/极端情况下的系统表现
- 架构 → 产品：评估技术实现成本、指出过度设计或不可行环节
- 每个对抗方向至少提出 2 个具体问题，总计 ≥3 个真实问题

**2.3 结论汇总**

按 `smoke_analysis.md` 第三阶段执行，输出：

- 关键风险表（序号/风险描述/涉及角色/严重程度/建议措施）
- 架构建议
- 产品建议
- 测试重点
- **冒烟测试范围建议**（建议纳入冒烟的核心功能点）

**2.4 P0 功能拆分**

按 `smoke_decomposition.md` 执行，仅拆分 P0 功能点：

- 功能模块树（仅 P0，标注依赖关系）
- 对抗性验证（每个 P0 功能点自问：异常路径/边界条件/并发竞态/失败回滚/权限越界）
- 业务流程拆分（入口条件/正常路径/退出条件，仅 Happy Path）
- 数据变更点识别（创建/读取/更新/删除）
- 问题映射表（三方分析问题 → P0 功能点 → 覆盖状态）

输出进度标记：`[WF:done:冒烟-三方分析]`

### Step 3: 开发冒烟用例生成 + Excel 导出

基于 Step 2 的三方分析结论和 P0 功能拆分，按 `references/smoke_generation.md` 和 `references/smoke_output.md` 执行。

**3.1 冒烟用例生成**

按 `smoke_generation.md` 执行：

- **数量**：5-20 条，全部 P0（核心阻断级）
- **步骤**：每条 ≤5 步，精简可执行
- **前置**：开发本地可快速准备（允许：已登录/已创建测试数据；禁止：1000 条数据初始化/生产环境配置）
- **溯源**：每条用例标注「三方关联」字段，链接到 Step 2 分析结论中的风险项编号
- **覆盖**：三方分析中的关键风险必须有对应冒烟用例

**3.2 输出校验**

按 `smoke_output.md` 执行：

- 三方分析报告校验（三视角完整、红蓝对抗 ≥3 问题、结论含冒烟范围建议）
- 冒烟用例文档校验（编号无重复 `SMK-{模块}-{序号}`、字段齐全、步骤 ≤5、覆盖率检查）
- 双文档一致性检查（三方关联可追溯、术语统一）

**3.3 写入文件**

- 三方分析报告 → `{TASK_OUTPUT_DIR}/{需求名称}_三方分析.md`
- 冒烟用例 → `{TASK_OUTPUT_DIR}/{需求名称}_开发冒烟用例.md`

输出进度标记：`[WF:done:冒烟-用例生成]`

**3.4 Excel 转换**

```bash
python "{SKILL_DIR}/scripts/md2excel.py" "{TASK_OUTPUT_DIR}/{需求名称}_开发冒烟用例.md" "{TASK_OUTPUT_DIR}/{需求名称}_开发冒烟用例.xlsx"
```

- 转换失败则输出 `[XMind 转换失败] 原因：...`，继续后续工作

输出进度标记：`[WF:done:冒烟-导出]`

### Step 4: 需求分析 + 模块划分 + 场景分组 + 维度识别

**将 Step 2 三方分析的结论（关键风险/矛盾点/测试重点）作为本步骤的关键输入**，按 `generation_rules.md` 和 `test_dimensions.md` 执行。

**4.1 模块划分**

章节标题为父模块，表格每行为子模块。核心原则：章节优先 + 父级保留。配置层章节仅输出合并描述，不生成用例。

**三方喂养**：Step 2 中识别出的矛盾/风险点，在模块划分阶段标记到对应的功能模块上。若某模块在三方分析中被标记为高风险，该模块的 P0 功能点优先纳入冒烟范围验证。

**4.2 输出需求提取清单（强制）**

逐句扫描 PRD，提取功能点并编号，标注来源位置。每条清单必须映射到用例或待澄清问题。**与 Step 2 的问题映射表交叉校验**——Step 2 中已识别的问题在清单中不得遗漏。

**4.3 场景分组**

模块内按操作场景分组，同一场景的正常/分支/异常用例放同一分组。场景命名格式：`{操作对象}-{关键条件/动作}`。

**4.4 校验链分组**

顺序校验模块按校验环节分组，每个环节包含正常/分支/异常用例。第一个校验环节上方增加汇总用例。

**4.5 PRD 自身矛盾检测**

基于 Step 2 已发现的问题，补充检测：前后描述不一致、图文不一致、术语不一致、参数不一致、流程矛盾。记录到完整性检查报告。高/中影响程度同时记入待澄清问题。

**4.6 测试维度识别**

为每个功能点按 `test_dimensions.md` 判断触发的测试维度（D1-D12）。**Step 2 中三方分析标注的测试重点方向，优先覆盖对应维度。**

**4.7 优先级定义**

P0=核心阻断 / P1=重要功能 / P2=次要功能 / P3=体验优化。与 Step 2 的风险严重程度对齐——高风险功能点至少为 P1。

Step 4 全部完成后，输出进度标记：`[WF:done:需求分析]`

**用例模板：**

```

  - {前置条件}，{测试动作}【主动补充】【自动化:是】
```

**关键原则：**

- 预期结果逐条展开为子节点，不使用模糊词
- 主动补充标注 `【主动补充】`，关联图片标注紧跟对应预期结果行尾

**三方喂养**：Step 2 中识别出的矛盾/风险/测试重点，在用例生成阶段体现为：(1) 矛盾相关的功能点生成额外边界/异常用例；(2) 高风险功能点确保覆盖 D1-D5 全维度；(3) 三方分析的待澄清问题逐条映射到用例或 Q 编号。

- 所有输出文件写入 `{TASK_OUTPUT_DIR}`，禁止写入沙箱外路径
