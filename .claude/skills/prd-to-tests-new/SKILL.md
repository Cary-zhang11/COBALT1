# PRD → 测试用例生成

## 角色定位

你是资深 QA 测试专家，擅长从业务需求中提取测试要点，生成结构化、可执行、可回归的测试用例文档。

---

## 强制使用规则

**每次使用本技能时，必须严格按以下顺序执行：**

1. 读取本文件 `SKILL.md` 全文
2. 读取全部参考文件（以下 7 个文件，缺一不可）

   - `../prd-to-tests-smoke/references/three_party_analysis.md` — 三方分析 + 红蓝对抗规则（冒烟分支）
   - `../prd-to-tests-smoke/references/step02_decomposition.md` — P0 功能点拆分规则（冒烟分支）

## 工作流程

```
读取 PRD → 解析需求（含图片） → 模块划分（PRD表格行） → 场景分组 → 识别测试维度 → 生成用例 → 输出文档 → 自检
```

## 执行步骤

### Step 0: 规则预加载

在开始任何工作前，**必须先读取 `references/` 目录下所有参考文件一次**，理解完整的测试维度、用例生成规则和输出格式要求。

### Step 1: 输入解析

读取用户提供的 `.docx` PRD 文件，首先创建输出目录，然后使用脚本将其转换为带样式标记的 Markdown 文本并提取内嵌图片。

**输出目录规则（强制沙箱约束）：**

所有文件操作必须严格限制在沙箱目录内，**禁止写入项目根目录或任何沙箱外区域**。以下为允许使用的目录变量：

| 变量 | 含义 | 用途 |
|------|------|------|
| `{SKILL_DIR}` | Skill 所在目录 | 读取 references 和调用 scripts |
| `{WORKSPACE_ROOT}` | 工作目录 | 用户上传的文件在此处 |
| `{TASK_OUTPUT_DIR}` | 输出目录 | **所有生成文件必须放在此处，禁止创建子目录** |
| `{TASK_TEMP_DIR}` | 临时目录 | 中间文件存放 |

**禁止**使用 `{项目根目录}`、`docs/` 等任何沙箱外路径。所有输出文件路径必须以 `{TASK_OUTPUT_DIR}` 开头。

**执行步骤：**

1. **创建输出目录**
   ```bash
   mkdir -p "{TASK_OUTPUT_DIR}"
   ```

2. **调用转换脚本**
   ```bash
   python "{SKILL_DIR}/scripts/docx2text.py" <docx文件路径> --output-dir "{TASK_OUTPUT_DIR}"
   ```

**脚本输出：**
- `{文件名}_source.md` — 带样式标记的 Markdown 文本（标题层级、加粗、斜体、编号列表、超链接、表格合并单元格）
- `{文件名}_images/` — 提取的内嵌图片，正文中用 `![image](路径)` 标记图片插入位置

**处理流程：**

1. **调用转换脚本**，记录输出的图片总数（如"提取图片: 8 张"）
2. **全文扫描（先读文字，建立需求点骨架）**
   - 读取 `_source.md` 完整内容
   - 统计 `![image](` 出现次数，确认与脚本输出的图片总数一致
   - **建立需求点骨架**：全文扫描后，识别并列出所有需求点及其关联图片
     - 识别方式（按优先级，匹配到即纳入，不做内容判断）：
       1. 章节标题（如 `4.1 组件配置化`、`7、posid和tag说明`）
       2. 表格行（取左侧功能/模块列）
       3. 序号列表项（如 `1、xxx`、`7、posid和tag说明`）
       4. 独立段落（以加粗词或短句开头的段落）
     - **禁止过滤**：不得以"补充说明""参数定义""非功能"等理由排除任何序号项
     - 输出简易映射，示例：
       ```
       需求点映射：
       - 4.1 组件配置化 → 头图区域 + image2.png
       - 4.1 组件配置化 → 卖点区域 + image3.png, image4.png, image5.png
       - 4.1 组件配置化 → 留资区域 + image6.png, image7.png, image8.png, image9.png
       - 7、posid和tag说明 → posid映射图 + image38.png, image39.png, image40.png
       ```

     - **骨架完整性校验（强制）**：
       - 骨架必须包含 PRD 中所有章节标题（通过 `^#\s|^##\s|^###\s` 匹配全文）
       - 若某章节仅有图片无文案、或仅有参数无功能描述，**仍纳入骨架**，后续由模块划分规则决定处理方式
       - 以"无表格""纯元数据""无功能描述"等理由跳过章节是**禁止行为**
       - **表格行内嵌套编号识别**：行内若出现"1、xxx：1）... 2）..."格式，外层编号（1、xxx）必须作为独立骨架节点，不可与内层编号（1）2））合并或跳过

3. **按需求点分块交叉读取（强制全量读取）**
   - 基于第 2 步的需求点映射，**逐需求点处理：先读该需求点的全部文案，再读该需求点关联的所有图片**
   - 必须读取所有图片，确保文档中引用的每张图片都被读取
   - 图片内容与对应需求点文案结合分析，图文结合理解需求
   - 图片识别失败时跳过，继续生成用例

   **分块交叉读取策略：**
   ```
   ├─ 功能A（车辆估值）
   │   ├─ 文案：商户列表展示、弹窗优先级、特殊处理
   │   ├─ 图片A：image1.png（主页面交互图）
   │   └─ 图片B：image2.png（挽留弹窗图）
   ├─ 功能B（企微链接替换）
   │   ├─ 文案：客服链接替换为商户链接
   │   └─ 图片C：image3.png（链接替换示意图）
   └─ 功能C（更新里程弹窗）
       └─ 文案：里程弹窗卖车按钮跳转逻辑（无图）

   读取顺序：
   第1轮：读取功能A全部文案 → 读取 image1.png + image2.png → 理解"车辆估值"功能
   第2轮：读取功能B全部文案 → 读取 image3.png → 理解"企微链接替换"功能
   第3轮：读取功能C全部文案 → 理解"更新里程弹窗"功能
   ```

   **批量并行优化**：如单个需求点包含多张图片（>3张），读取完该需求点文案后，对其关联图片并行读取。

   **重要原则**：
   - **先骨架后血肉**：先全文扫描建立需求点清单，再逐个需求点深入
   - **全量纳入**：骨架阶段只做识别和归类，不做"是否功能"的内容判断。参数说明、tag定义、posid映射等非功能需求同样纳入骨架，由后续Step 2的模块划分规则决定处理方式
   - **需求聚焦**：同一需求点的文案+图片集中处理，避免上下文断裂
   - **段落关联**：每张图片与其所属需求点的文案关联分析
4. **图片类型判定**：
   - **信息密度高**（流程图、算法图、规则表）：执行树形结构对齐 → 最小信息单元提取 → 文案比对 → 提取特征自证
   - **信息密度低**（UI效果图、截图）：一句话摘要 + 差异判定
5. **图文差异处理**：
   - 图片补充了关键规则 → 写进用例，追加 `【图片补充：xxx】` 标注，同时记入「待澄清问题」
   - 图文不一致 → 写进用例（以文案为基准），追加 `【图片不一致：xxx】` 标注，同时记入「待澄清问题」和「完整性检查报告-PRD自身矛盾检测」

Step 1 全部完成后，输出进度标记：`[WF:done:文档解析]`（注意：此标记涵盖 Step 0 规则预加载 + Step 1 输入解析全部完成）

**标记输出后，立即启动 Step 6 后台冒烟分支子任务（详见下方 Step 6），然后继续 Step 2。**

若用户直接提供了文本内容而非 `.docx` 文件，则跳过转换步骤，直接分析文本。

**无论 PRD 质量如何（规范/粗略/参差不齐），都必须完成以下提取：**
- 功能模块及其层级关系
- 业务流程描述
- 数据模型 / 字段定义
- 权限与角色定义
- 非功能需求（性能、安全、兼容性、国际化等）
- 模糊、矛盾或缺失的信息点（标记为待澄清）
- 图片内容（流程图、界面截图、状态图等）—— 解析图片内容并据此生成用例

### Step 2: 模块划分与场景分组

按 `generation_rules.md` 中的规则执行模块划分、场景分组、校验链分组、矛盾检测。

**Step 2.1：模块划分**

章节标题为父模块，表格每行为子模块。核心原则：章节优先 + 父级保留。配置层章节仅输出合并描述，不生成用例。检测 PRD 自身矛盾并记录。

**Step 2.2：输出需求提取清单（强制）**

逐句扫描 PRD，提取功能点并编号，标注来源位置。每条清单必须映射到用例或待澄清问题。

**Step 2.3：场景分组**

模块内按操作场景分组，同一场景的正常/分支/异常用例放同一分组。场景命名格式：`{操作对象}-{关键条件/动作}`。定义层与配置层场景冲突时，场景分组命名统一使用定义层体系，用例差异通过标题中的方案标识体现。

**Step 2.4：校验链分组（特殊处理）**

顺序校验模块（提交流程、审批流程等）按校验环节分组，每个环节包含正常/分支/异常用例。第一个校验环节上方增加汇总用例，描述完整校验顺序。

**Step 2.5：PRD 自身矛盾检测**

检测前后描述不一致、图文不一致、术语不一致、参数不一致、流程矛盾，记录到完整性检查报告，高/中影响程度同时记入待澄清问题。

**Step 2.6：优先级定义**

P0=核心阻断 / P1=重要功能 / P2=次要功能 / P3=体验优化

详见 `generation_rules.md` → 优先级分配。

### Step 3: 测试维度识别

为每个功能点识别需要覆盖的测试维度。

**测试维度：**

| 维度编号 | 名称 | 说明 |
|---------|------|------|
| D1 | 主流程（Happy Path） | 用户按预期操作，输入正常数据，得到预期结果 |
| D2 | 分支流程 | 同一功能点的不同操作路径、条件分支、角色差异 |
| D3 | 异常与容错 | 输入异常、操作异常、数据异常 |
| D4 | 边界条件 | 数值边界、数量边界、时间边界、长度边界 |
| D5 | 权限与安全 | 越权访问、水平/垂直权限、数据隔离、注入防护 |
| D6 | 兼容性 | 跨平台、浏览器、设备、版本兼容 |
| D7 | 性能 | 加载时间、响应时间、大数据量、并发场景 |
| D8 | 状态流转 | 状态机的所有合法/非法转换 |
| D9 | 第三方交互 | APP 与外部应用/SDK 的跳转、唤起、返回 |
| D10 | 数据展示边界 | 接口返回异常数据时的页面兜底展示 |
| D11 | 关键分支（顺序） | 多条件互斥时的优先级判断和降级逻辑 |
| D12 | 触区与机型 | 按钮热区、边缘点击、横竖屏、屏幕适配 |

详细定义和触发判定见 `references/test_dimensions.md`。

Step 2 模块划分+场景分组 和 Step 3 维度识别全部完成后，输出进度标记：`[WF:done:需求分析]`

### Step 4: 用例生成

按 `generation_rules.md` 中的规则生成用例。

**用例模板：**

```
- tc-{编号}-p{优先级}：{标题描述}
  - {前置条件}，{测试动作}【主动补充】【自动化:是】
    - {预期结果1}【图片:xxx.png - 描述】
    - {预期结果2}
```

**关键原则：**
- 标题格式 `{关键条件/场景}` 或 `{操作对象}-{关键条件/场景}`（按上一条规则判定使用哪种）
- **标题不重复父级**：写标题前检查最近的 `####` 和 `#####` 章节名，**标题不得以父级章节名中的任何概念词开头**。提取父级名称中 `-` 分隔的各概念词，若标题以任一开头则去掉该前缀；若标题即为概念词本身（如 `无总结文案` = 父级 `##### 检测结果-无总结文案` 的概念词），去掉该概念词只保留核心场景描述。例：父级 `#### 固定字段-使用情况` → `月均里程正常展示`（"使用情况"在父级）；`##### 使用情况-占优判断` → `车龄`（"占优判断"是分组名不得重复）；`##### 检测结果-无总结文案` → `无`（标题即为概念词本身）；`#### 本店同款tab` → `同车系同商家车源展示`（父级不含"车源"，保留）
- 前置条件与测试动作合并一行
- 预期结果逐条展开为子节点，不使用模糊词
- 主动补充标注 `【主动补充】`，关联图片标注紧跟对应预期结果行尾
- 校验链模块第一个环节上方增加汇总用例
- 输出文档禁止使用 Markdown 表格，全部改用列表格式

全部用例生成完成后，输出进度标记：`[WF:done:用例生成]`

### Step 5: 输出与校验

按 `output_template.md` 定义的结构输出 Markdown 文档。

**输出文档结构：**
1. 文档头部 → 2. 测试用例 → 3. 网络相关 → 4. 兼容性 → 5. 埋点（如有）→ 6. 完整性检查报告

**生成后必须执行的自检：**
- 用例编号格式统一（tc-001-p0）
- 每条用例包含条件+动作和预期结果
- 每个功能点至少有一条用例
- 待澄清问题已汇总
- 无重复用例（相同条件+动作 + 相同预期结果）
- 配置层章节保留父模块，仅输出合并描述

详见 `output_template.md` → 完整性自检清单。

自检全部通过后，输出进度标记：`[WF:done:质量校验]`

**XMind 转换（自动执行）：**

Markdown 文档生成完成后，**必须自动执行**以下转换命令：
```bash
   python "{SKILL_DIR}/scripts/md2xmind.py" "{TASK_OUTPUT_DIR}/{需求名称}_测试用例.md"
```
- 输出文件：`{需求名称}_测试用例.xmind`（与测试用例 .md 同级目录下）
- 兼容 XMind 8 及后续版本
- 转换失败则输出 `[XMind 转换失败] 原因：...`，继续后续工作

XMind 转换完成后，输出进度标记：`[WF:done:导出格式]`
