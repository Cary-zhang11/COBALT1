# Step 4: 开发冒烟用例生成

## 目标
基于 PRD 原始需求和三方分析结论，生成精简、可执行的开发冒烟测试用例。

## 冒烟用例定义

冒烟测试（Smoke Test）是覆盖系统核心主流程的最小测试集合，目的是快速验证"系统是否值得进一步测试"。

### 核心特征
- **数量精简**：通常 5-20 条，只覆盖最关键路径
- **只取主流程**：仅包含 Happy Path，不覆盖异常和边界
- **步骤简洁**：每条用例步骤不超过 5 步，适合开发快速执行
- **前置条件简单**：不需要复杂的数据准备或环境配置
- **结果明确**：通过/失败判断标准清晰，无二义性
- **优先级统一**：全部为 P0（核心阻断级）

## 生成规则

### 规则 1：只从 P0 功能点选取
冒烟用例只来源于功能拆分中标记为 P0 的功能点。若某核心流程涉及多个 P0 功能点，合并为一条端到端用例。

### 规则 2：步骤极简
每条用例的测试步骤严格控制在 5 步以内。步骤描述使用开发可执行的精确操作，避免"适当""可能"等模糊词。

### 规则 3：结合三方结论
生成冒烟用例时，必须参考三方分析结论中的以下内容：
- **关键风险**：高风险功能点必须生成冒烟用例
- **架构建议**：涉及数据一致性、状态流转的功能必须验证
- **测试重点**：三方标出的重点方向优先纳入冒烟范围
- **接口完整性**：核心接口的入参/出参校验纳入冒烟

### 规则 4：前置条件最小化
冒烟用例的前置条件必须是开发本地可快速准备的：
- 允许："已登录管理员账号"、"已创建测试数据 X"
- 不允许："已完成 1000 条数据初始化"、"已配置生产环境"

### 规则 5：预期结果可一键验证
预期结果必须是开发执行后可立即判断的：
- 页面跳转、数据状态变更、接口返回码
- 允许检查数据库（因为开发有权限）
- 不需要检查邮件/短信等异步通知

## 用例模板

每条冒烟用例严格按以下格式生成：

```
### SMK-{模块}-{序号} | P0 | {用例标题}

- **所属模块**: {模块名称}
- **功能点**: {关联功能点编号及名称}
- **前置条件**:
  1. {条件 1}
- **测试步骤**:
  1. {步骤 1}
  2. {步骤 2}
- **预期结果**:
  - 步骤 1 预期: {结果}
  - 步骤 2 预期: {结果}
  - 最终预期: {最终状态}
- **三方关联**: {关联的三方分析结论编号或风险项}
```

### 用例标题

用一句话描述"做什么 + 什么条件下"，格式：

```
{操作} - {条件 / 场景}
```

示例：
- `提交订单 - 库存充足`
- `用户登录 - 正确账号密码`
- `创建项目 - 必填字段完整`

### 前置条件

列出执行该用例前必须满足的状态，控制在 2 条以内：
- 用户已登录且具备必要角色
- 必要的前置数据已创建

### 测试步骤

- 每步描述一个用户操作或系统动作
- 使用"动作 + 对象"的句式，如"点击提交按钮""输入用户名 admin"
- 步骤编号连续，不跳跃
- **步骤数量严格控制在 5 步以内**
- 若超过 5 步，考虑拆分为多条用例或合并步骤

### 预期结果

- 与测试步骤一一对应
- **原子化**：如果预期结果包含多个独立校验点，拆分为多条子项
- 预期结果必须可判定（能通过 / 不通过）
- 包含数据变更验证和 UI 反馈验证

## 用例数量控制

每条用例独立可执行，有明确的通过 / 不通过判定。避免：
- 将多个无关场景合并为一条用例
- 生成纯理论性的极端场景

参考数量范围（按需求复杂度调整）：
- **简单项目**：5-8 条用例
- **中等项目**：8-15 条用例
- **复杂项目**：15-20 条用例（超过 20 条需说明原因）

## 编号规则

```
SMK-{模块缩写}-{序号}
```

示例：`SMK-USER-01` 表示用户模块第 1 条冒烟用例。

## 完整性校验

生成后检查：
- [ ] 用例数量在 5-20 条之间（超出需说明原因）
- [ ] 每条用例步骤不超过 5 步
- [ ] 所有用例优先级均为 P0
- [ ] 三方结论中的关键风险均有对应冒烟用例
- [ ] 前置条件均为开发本地可快速准备的
- [ ] 编号无重复，格式统一
