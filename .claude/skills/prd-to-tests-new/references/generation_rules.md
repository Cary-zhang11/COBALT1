# 用例生成规则

## 模块划分规则

### 核心原则

**章节优先 + 父级保留**

- **所有章节标题都成为父模块**（二级编号，如 1.1, 1.2, 1.3...），章节是模块划分的第一依据
- 章节下的表格每一行作为子模块（三级编号，如 1.1.1, 1.1.2...）
- 行内功能子项按功能独立性判断是否提升（四级编号）
- 层级不强制、不降级：由功能粒度自然决定，父模块不可跳过

### ⚠️ 需求不能过滤跳过

PRD 文件中的**所有章节都必须参与用例生成**，不存在"不可测试""纯元数据""补充说明"等可以跳过的章节类型。以"不可测试""纯元数据""内容已覆盖"等理由跳过 PRD 章节或需求内容是**禁止行为**。

- 有功能描述（表格/流程/规则）→ 正常生成用例
- 有参数说明（posid/tag/pvareaid 等）→ 生成参数验证用例
- 有实验计划（对照组/实验组/兜底）→ 生成实验行为用例
- 有排除约束（如"XX 场景不命中"）→ 提取到公共前置或待澄清
- 工单链接/版本号/设计稿 → 写入文档头部元数据

### 章节分类规则

所有章节按功能性质分类处理：

| 类型 | 关键词参考 | 处理方式 |
|------|-----------|---------|
| 特殊章节 | 埋点、数据上报、网络、兼容、性能、安全 | 提升为顶层独立模块（二/三/四） |
| 配置层 | 方案一/二/三、变体A/B/C、Plan、Mode | 保留父模块，仅输出合并描述 |
| 定义层 | 通用能力、组件配置化、其他能力、功能说明 | 保留父模块，正常生成用例 |
| 普通功能 | 具体功能名称 | 保留父模块，正常生成用例 |

> 关键词仅作参考，核心判断依据是**章节内容的功能性质**。

### 配置层合并规则

配置层章节保留父模块标题（二级标题），占用编号，内容仅输出结构化合并描述，不生成用例。**禁止使用 `>` 引用块**（XMind 转换不兼容），改用列表格式。

**合并描述格式**：
```markdown
### 1.{N} {配置层章节名称}（合并到定义层）

- 本章为配置层，内容已合并到定义层对应模块：
  - {配置层子项1}（{差异简述}）→ {定义层编号} {定义层名称}
  - {配置层子项2}（{差异简述}）→ {定义层编号} {定义层名称}
- URL 参数完整列出：{标题下方的完整 URL 参数，不解析不拆分}
```

**配置层优先级**：当配置层与定义层对同一功能有不同描述时，**配置层优先级高于定义层**。用例以配置层为准，通过"命中方案X"的前置条件区分。

**用例中的方案标识**：定义层各模块的用例标题中保留方案标识（如"命中方案一"、"命中方案三"），实现双向追溯。方案一和方案二对同一功能描述完全一致时，用例合并为一条，标题标注"方案一/二"。

**场景冲突处理**：定义层与配置层场景冲突时，场景分组命名统一使用定义层体系，用例差异通过方案标识体现，不创建重复的场景分组。

### ⚠️ 无表格章节强制提取

当章节不含表格但包含关键规则/参数/配置时，**不可跳过**，按以下方式处理：

| 章节类型 | 识别关键词 | 处理方式 |
|---------|-----------|---------|
| 实验/AB测试 | 实验、AB、对照、实验组、对照组、testver、兜底 | 提升为独立子模块，生成实验验证用例（对照组/实验组/兜底行为各一条） |
| 参数/ID映射 | posid、tag、参数说明、枚举值、ID、编号 | 提升为独立子模块，生成参数验证用例 |
| 埋点/数据上报 | 埋点、数据上报、事件、上报 | 按埋点用例生成规则处理，不归属到单一功能模块 |
| 工单/链接/设计稿 | 工单、链接、设计稿、zip、下载 | 写入文档头部元数据，不生成用例 |
| 其他纯文本章节 | 上述均不匹配 | 逐句提取为场景分组，不可跳过 |

**注意：** 即使章节仅含图片或仅含参数定义而无功能描述，也必须纳入骨架，后续由模块划分规则决定处理方式。以"无表格""纯元数据""无功能描述"等理由跳过章节是**禁止行为**。

### 划分方式

**方式 1：有章节标题 + 表格**

章节作为父模块（二级标题），表格每行作为子模块（三级标题）。

**示例**：

PRD 结构：
```
4.1 组件配置化

| 组件区域 | 描述 | 示意图 | 埋点 |
| --- | --- | --- | --- |
| 头图区域 | ... | ... | ... |
| 卖点区域 | ... | ... | ... |
```

输出模块结构：
```markdown
### 1.1 组件配置化（来自PRD章节4.1）

#### 1.1.1 头图区域（来自PRD表格第1行）
#### 1.1.2 卖点区域（来自PRD表格第2行）
```

**方式 2：有章节标题 + 段落**

章节作为父模块（二级标题），段落内容逐句/逐条提取为场景分组（四级标题）或功能子项。**独立章节标题即代表独立模块，直接提升为子模块，不需要判断功能独立性门槛**。

**方式 3：无章节标题的表格（兜底）**

当表格无章节标题包裹时，退回到"一行一个模块"：

```
### 1.1 头图区域（来自PRD表格第1行）
### 1.2 卖点区域（来自PRD表格第2行）
### 1.3 留资区域（来自PRD表格第3行）
```

**方式 4：无章节标题的段落（兜底）**

按段落标题或功能独立性划分模块。

### 行内功能子项处理

- **普通并列描述项**（无结构分隔、无功能独立性，如"支持静态图片<br>支持动态图片"）：作为模块内场景分组（四级标题 `#####` 或五级标题 `######`），不提升
- **有结构分隔且功能独立的子项**（编号段落/小标题/段落分隔 + 独立前置条件/交互/预期结果）：提升为功能子项（四级标题），其下再分场景分组（五级标题）

**判断标准（两层判断，同时满足）：**
- 结构分隔：编号段落（1、xxx）、小标题（**xxx**：）、段落分隔（换行或 `<br>` 分隔的多段落）
- 功能独立性：独立前置条件/状态判断、独立交互逻辑、独立预期结果集

**示例 1 - 普通并列项（不提升）：**

PRD 表格行内容：
```
头图区域 | 支持静态图片<br>支持动态图片<br>支持视频 | ...
```

输出：
```markdown
#### 1.1.1 头图区域（来自PRD表格第1行）
##### 1.1.1.1 头图-静态图片  ← 场景分组
##### 1.1.1.2 头图-动态图片
##### 1.1.1.3 头图-视频
```

**示例 2 - 功能独立子项（提升）：**

PRD 表格行内容：
```
完善信息、成交价、加油站 | ...<br>1、车辆和品牌：有车时...无车时...<br>2、市场行情：无车时...有车时...<br>3、卖车加油站：固定展示...
```

输出：
```markdown
#### 1.5.3 完善信息、成交价、加油站（来自PRD表格第3行）
##### 1.5.3.1 车辆和品牌  ← 功能子项（四级标题）
###### 1.5.3.1.1 车辆-有车  ← 场景分组（五级标题）
###### 1.5.3.1.2 车辆-无车
##### 1.5.3.2 市场行情
###### 1.5.3.2.1 行情-无车
###### 1.5.3.2.2 行情-有车
##### 1.5.3.3 卖车加油站
###### 1.5.3.3.1 加油站-展示
```

**嵌套编号处理：** 当行内编号子项（如 `**1、车辆和品牌：**`）自身仍包含编号分组（如 `1）有车 2）无车`），执行两层提升：
1. 外层编号（1、2、3 或 一、二、三）→ 提升为功能子项（`#####`）
2. 内层编号（1）、2）或 ①②）→ 提升为场景分组（`######`）

**⚠️ 禁止跳过外层编号**：外层编号（如"车辆和品牌"）必须作为独立的 `#####` 父节点输出，不可省略。即使外层编号下只有1个内层场景，也必须保留外层父节点。

编号符号识别：任意编号形式均触发规则（`1、` / `一、` / `(1)` / `①` / `【1】` / 第一步/第二步 等）。

**示例 3 - 嵌套编号：**

PRD 表格行内容：
```
完善信息、成交价、加油站 | **1、车辆和品牌：**<br>1）有车时：展示车+品牌...<br>2）无车时：仅展示品牌...<br>**2、市场行情：**<br>1）无车时：点击添加...<br>2）有车时：正常展示...
```

输出：
```markdown
#### 1.5.3 完善信息、成交价、加油站（来自PRD表格第3行）
##### 1.5.3.1 车辆和品牌
###### 1.5.3.1.1 有车
- tc-101：正常展示车+品牌
###### 1.5.3.1.2 无车
- tc-103：仅展示品牌
##### 1.5.3.2 市场行情
###### 1.5.3.2.1 无车
- tc-104：添加旧车
###### 1.5.3.2.2 有车
- tc-105：正常展示
```

**❌ 错误示例（跳过外层编号，禁止）：**
```markdown
#### 1.5.3 完善信息、成交价、加油站
##### 1.5.3.1 有车         ← 错误！跳过了"车辆和品牌"父节点
##### 1.5.3.2 无车         ← 错误！跳过了"车辆和品牌"父节点
```

**无编号功能关键词识别：** 当段落无编号但包含以下关键词模式，也拆分为场景分组：

关键词模式：
- 条件词：有...时/无...时/已.../未.../首次/再次
- 状态词：登录态/非登录态/有车/无车/已选择/未选择
- 分支词：如...则.../若.../否则/反之

**示例 4 - 无编号功能关键词：**

PRD 表格行内容：
```
车辆和品牌 | 有车时展示车+品牌，无车时仅展示品牌
```

输出：
```markdown
##### 1.X.X 车辆和品牌
###### 1.X.X.1 有车
- tc-xxx：正常展示车+品牌
###### 1.X.X.2 无车
- tc-xxx：仅展示品牌
```

## 模块内分组规则

### 分组原则

**按操作场景分组，不按测试类型分组**

模块内用例按用户操作场景组织，同一场景的正常/分支/异常用例放在同一分组内，便于理解业务流程完整性。

### 场景命名规则

格式：`{操作对象}-{关键条件/动作}`

**命名模板：**
- `{对象}-{动作}`：头图-点击、品牌-选择
- `{对象}-{状态}`：协议-未勾选、协议-已勾选
- `{对象}-{条件}`：手机号-登录态、手机号-非登录态
- `{环节}-{结果}`：协议校验-拦截、协议校验-放行

### 递进子概念分组

当 PRD 同一段落内出现明确子概念标题（如"第一步/第二步"、"占优判断"、"总结文案"、"计算规则"），提升为 `##### {子概念名}` 分组包裹各自用例。

示例：
```
#### 使用情况模块
- tc-055-p0：6字段展示
- tc-056-p0：差异高亮

##### 占优判断
- tc-061-p0：车龄
- tc-062-p0：交强险到期

##### 总结文案
- tc-065-p0：当前车占优≥5项
- tc-066-p0：当前车占优=4项
```

### 分组编号规则

模块内分组编号挂在子模块下，层级由功能粒度自然决定：
- 子模块 → 场景分组：三级编号 `1.1.1`, `1.1.2`...
- 子模块 → 功能子项 → 场景分组：四级编号 `1.5.3.1`, `1.5.3.2`... → 五级编号 `1.5.3.1.1`, `1.5.3.1.2`...

## 校验链分组规则

### 适用范围

**适用于所有包含顺序校验的模块**

当模块涉及多个环节的顺序校验时，按校验环节分组。适用场景包括：
- 提交流程（协议 → 校验 → 提交）
- 审批流程（草稿 → 提交 → 审批 → 完成）
- 状态流转（状态A → 状态B → 状态C）
- 注册流程（填写信息 → 验证 → 创建账号）
- 支付流程（选择方式 → 校验 → 支付 → 完成）

### 分组方式

**每个校验环节作为独立分组**

将顺序校验拆分为多个环节，每个环节作为一个三级分组。

**示例 1：提交模式模块**

校验链：协议 → 城市区县 → 手机号 → 30线索 → 车辆 → 二次确认 → 风控 → 600线索 → 补邀约 → 660线索

分组：
- 1.1.4.1 协议校验
- 1.1.4.2 城市区县校验
- 1.1.4.3 手机号校验
- 1.1.4.4 30线索校验
- 1.1.4.5 车辆校验
- 1.1.4.6 二次确认
- 1.1.4.7 风控校验
- 1.1.4.8 600线索提交
- 1.1.4.9 补邀约
- 1.1.4.10 660线索提交

**示例 2：审批流程模块**

校验链：草稿 → 提交 → 主管审批 → 财务审批 → 完成

**在第一个校验环节上方增加汇总用例：**
```
- tc-XXX-p0：{模块名}-统一校验顺序
  - 触发完整校验流程
    - 按以下顺序依次校验：草稿 → 提交 → 主管审批 → 财务审批 → 完成
    - 任意环节已完成的项自动跳过
```

分组：
- 1.X.X.1 草稿状态
- 1.X.X.2 提交申请
- 1.X.X.3 主管审批
- 1.X.X.4 财务审批
- 1.X.X.5 审批完成
- 1.X.X.6 驳回处理




### 每环节用例内容

每个校验环节分组内，包含该环节的全部用例：

| 用例类型 | 说明 | 是否必须 |
|---------|------|---------|
| 正常通过场景 | 该环节正常校验通过 | 必须 |
| 分支处理场景 | 跳过、替代路径、条件差异 | 按需求判断 |
| 异常拦截场景 | 校验失败、条件不足、拦截提示 | 必须 |
| 边界条件 | 该环节涉及的边界值 | 按需求判断 |

**示例：协议校验环节的完整用例**

```
#### 2.1.1 协议校验

- tc-001-p1：协议校验-未勾选拦截
  - 未勾选协议，点击提交按钮
    - 弹出协议选择弹层，用户同意后方可继续

- tc-002-p0：协议校验-已勾选放行
  - 已勾选协议，点击提交按钮
    - 不弹出协议弹层，直接进入下一校验环节

- tc-003-p2：协议弹层-用户同意
  - 未勾选协议，弹出协议选择弹层，点击同意按钮
    - 协议勾选框自动勾选，进入下一校验环节

- tc-004-p2：协议弹层-用户拒绝
  - 未勾选协议，弹出协议选择弹层，点击拒绝按钮
    - 弹层关闭，协议保持未勾选，停留在当前页面
```

## PRD 自身矛盾检测规则

### 检测目标

在需求提取阶段，检测 PRD 文档自身存在的矛盾和不一致，并记录到完整性检查报告中。

### 检测范围

| 矛盾类型 | 说明 | 示例 |
|---------|------|------|
| 前后描述不一致 | 同一功能在文档不同位置的描述存在矛盾 | 前文定义A/B/C/D/E五种模式各独立流程，后文用统一流程覆盖 |
| 图文不一致 | 文字描述与图片内容不符 | 文字说"按钮居右"，图片显示按钮居左 |
| 术语不一致 | 同一概念使用不同术语 | 前文称"订单号"，后文称"订单ID" |
| 参数不一致 | 同一参数在不同位置的取值规则不同 | 前文说"用户名长度1-50"，后文表格写"用户名长度≤100" |
| 流程矛盾 | 流程描述存在逻辑矛盾 | 状态流转图显示A→B→C，文字描述A可直接到C |
| 优先级矛盾 | 同一功能的优先级在不同位置标注不同 | 表格标注P0，说明文字标注P1 |

### 检测方法

**方法 1：同主题内容比对**

当同一功能/模块在 PRD 中多次出现时，比对各处的描述是否一致。

**示例：**

PRD 内容：
```
提交模式（第3行）：
- 模式A：协议→手机号→30线索→车辆→城市区县→二次确认→风控→600→补邀约→660
- 模式B：协议→车辆→城市区县→二次确认→风控→600→补邀约→660
- 模式C：协议→手机号→车辆→二次确认→风控→600→补邀约→660

*更新（第3行后补充）：
统一流程：协议→城市区县→手机号→30线索→车辆→二次确认→风控→600→补邀约→660
```

检测结果：
```
矛盾点：提交模式定义矛盾
- 前文定义A/B/C三种模式各有独立校验链路（A含手机号校验、B不含）
- 后文用统一流程覆盖五种模式
- 处理方式：已标注，记入待澄清问题 Q1
```

**方法 2：图文交叉比对**

当 PRD 包含图片时，比对图片内容与对应文字描述是否一致。

**示例：**

文字描述："服务人数位置靠左，成交历史轮播展示"
图片内容：服务人数居中，成交历史轮播隐藏

检测结果：
```
矛盾点：头图样式图文不一致
- 文字：服务人数靠左，轮播展示
- 图片：服务人数居中，轮播隐藏
- 处理方式：已标注【图片不一致:服务人数位置】，记入待澄清问题 Q2
```

**方法 3：术语统一性扫描**

全文扫描同一概念的术语使用是否统一。

**示例：**

前文："订单号自动生成，18位"
后文："订单ID需唯一"

检测结果：
```
矛盾点：订单标识术语不一致
- 前文使用"订单号"
- 后文使用"订单ID"
- 处理方式：已统一为"订单号"，在完整性检查报告中标注
```

### 矛盾处理方式

| 影响程度 | 处理方式 |
|---------|---------|
| 高（影响核心流程） | 生成用例（以最常见描述为准），记入待澄清问题，标注矛盾点 |
| 中（影响部分场景） | 生成用例，记入待澄清问题，标注矛盾点 |
| 低（术语/格式差异） | 统一术语，在完整性检查报告中标注 |

## 用例模板

### 基本格式

```
- tc-{编号}-p{优先级}：{标题描述}
  - {前置条件}，{测试动作}
    - {预期结果1}【图片:xxx.png - 描述】
    - {预期结果2}
    - {预期结果3}
```

### 字段说明

| 字段 | 格式规则 |
|------|---------|
| **编号** | `tc-{序号}-p{优先级}`，序号三位数字全局递增（001, 002, 003...），跨模块不重置 |
| **优先级** | 单字符：p0/p1/p2/p3 |
| **标题** | `{操作对象}-{关键条件/场景}`，括号内保留关键区分信息（如方案一/二、已登录、未勾选等） |
| **前置条件** | 精简描述核心条件，无前置条件时省略，直接写动作 |
| **测试动作** | 用户操作（点击、输入、选择、查看），多动作逗号分隔 |
| **预期结果** | 逐条展开为子节点，每条一个独立校验点 |

### 合并规则（前置条件与测试动作）

**格式：** `{前置条件}，{测试动作}`

| 场景 | 写法示例 |
|-----|---------|
| 有前置条件+单动作 | `未勾选协议，点击留资主按钮` |
| 有前置条件+多动作 | `7天内曾选择过城市，再次进入页面` |
| 无前置条件+单动作 | `查看头图区域` |
| 无前置条件+多动作 | `进入卖车页面，配置为宽卖点样式` |
| 复杂流程（>3步） | AI自行决定合并或拆分，保证可读性 |

**省略原则：** 已在模块公共前置中声明的条件，用例中省略，直接写动作。

### 前置条件显示规则

- 有前置条件：与测试动作合并为一行，逗号分隔
- 无前置条件：直接写动作，跳过"前置条件"字段

### 测试步骤编写

- 合并入条件+动作行，不单独成行
- 格式：`{条件}，{动作1}，{动作2}，{动作3}`
- 步骤数量由 AI 自行决定，保证可读性即可
- 每步精简描述核心操作

| 标签类型 | 位置 | 说明 |
|---------|-----|------|
| `【自动化:是】` | 条件+动作行尾 | 整个用例可自动化 |

## 合并规则

### 允许合并的情况

**操作步骤完全相同的场景可以合并为一条用例，预期结果分分支列出：**

示例：

```
- tc-005-p0：用户登录-不同密码场景
  - 用户已注册账号 test001，打开登录页输入用户名密码点击登录
    - 场景A（正确密码）: 页面跳转首页，右上角显示用户名
    - 场景B（错误密码）: 页面停留当前，提示「用户名或密码错误」
    - 场景C（账号已锁定）: 页面停留当前，提示「账号已被锁定」
```

### 不允许合并的情况

以下情况必须拆分为独立用例：
- **输入条件不同**（如测试不同字段值）
- **操作路径不同**（如不同页面入口、不同操作顺序）
- **涉及的模块或功能点不同**
- **边界值测试**（边界 ±1 各一条，不可合并）
- **等价类**（每个等价类各一条，不可合并）

---

## 拆分规则

### 优先按输入条件拆分

同一个功能点，不同输入条件导致不同处理结果的，各写一条用例：

- 字段为空 vs 字段有值 → 两条用例
- 合法值 vs 非法值 → 两条用例
- 不同枚举值 → 各一条用例（或按等价类合并）
- 边界值：最小值、最大值、最小值-1、最大值+1 → 各一条用例

### 其次按操作路径拆分

同一个功能点，不同操作路径各写一条用例：

- 通过菜单进入 vs 通过链接直达 → 两条用例
- 正常流程完成 vs 中途取消 → 两条用例
- 单人审批 vs 多人会签 → 两条用例

### 状态流转拆分

- 每个合法状态转换各一条用例
- 每个非法状态转换各一条异常用例
- 操作步骤相同但目标状态不同的，可合并为一条

## 测试方法提醒

**定位：用例生成阶段的思考维度，按需选用，不强制全用。看到什么信号就展开对应场景，不生成与需求无关的用例。**

### 边界值 — 数值边界点 ±1

**信号**：大于/小于/不超过/至少/最多/区间（如 `>3`、`≤50`、`XX~YY`、"每24小时"）
**展开**：边界值-1、边界值、边界值+1、0（数量/金额场景）、等于（两值比较场景）
**示例**：PRD「异常项 > 3项标红」→ 异常项=3（不红）+ =4（标红）各一条

### 等价类 — 不同输入类型各一条

**信号**：有X则A无X则B / 支持多种 / 为空时 / 不同等级
**展开**：有值 / 空值 / 非法值（或异常值）
**示例**：PRD「有认证报告展示"认证报告"，无则"暂无认证"」→ 有 + 无 + 获取失败各一条

### 逆向操作 — 操作的反面路径

**信号**：点击跳转 / 弹窗 / 确认弹层 / 选择器 / 编辑 / 移除
**展开**：弹层关闭或取消、返回上一页、快速连续操作
**示例**：PRD「点击「移除」删除对比车辆」→ 正常移除 + 移除后仅剩1台触发提示

### 数据一致性 — 跨页面/跨模块的联动

**信号**：自动刷新 / 同步到 / 计算结果 / 切换时
**展开**：修改数据后返回页面是否刷新、计算结果是否准确
**示例**：PRD「切换时对比内容自动刷新」→ 切换车源后所有模块数据更新

### 时序场景 — 定时/超时/高频操作

**信号**：每XX小时 / 倒计时 / 自动关闭 / 超时 / 连续点击
**展开**：刚好到时间点、超时重试、重复触发防抖
**示例**：PRD「网络异常展示toast」→ 弱网加载 + 接口超时 + 网络恢复后刷新

**使用原则**：按需选用，不强制全用；标题写具体场景值（如"异常项=3项"），不写方法名；延伸不超过PRD隐含的业务逻辑范围；主动扩展的用例加 `【主动补充】`。

## 防漏规则（需求提取阶段强制执行）

以下规则在读取 PRD 时生效，目的是防止需求点在提取阶段被遗漏。**所有规则均为强制要求，不可跳过。**

### 规则 1：表格/密集文本中的并列项必须拆分

当 PRD 以表格单元格、`<br>` 分隔列表、或一句话中用"和/或"连接多个功能项时，每个并列项都需单独验证，不可合并为一条用例。

**示例：**
- 「支持静态和动态图片」→ 静态图片一条用例 + 动态图片一条用例
- 「可编辑、可提交、可删除」→ 每个操作至少一条用例

### 规则 2：双向/多向条件必须全覆盖

当 PRD 出现"如 A 则 X，反之则 Y"或类似的正反双向描述时，必须为每个分支各生成一条独立用例，不可只覆盖其中一侧。

**示例：**
- 「协议已勾选则弹层同步勾选，未勾选则弹出协议选择」→ 两条用例
- 「登录手机号 > 用户主动一键获取手机号」→ 登录态一条 + 一键获取一条

### 规则 3：段落每一句话都必须映射

每个需求段落的每一句话都必须映射到至少一个用例或待澄清问题，不可跳过段落末尾的附加规则。长段落末尾的信息最容易遗漏，需特别注意。

**示例：**
- 「关闭按钮需增加挽留确认。每个设备每 24 小时弹出一次」→ 挽留确认一条 + 24 小时限制一条
- 「倒计时 15s 后自动关闭」→ 关闭动作一条 + 关闭后状态记录一条

### 规则 4：一句话需求若涉及交互也要展开

即使 PRD 只有一句话描述某个功能，只要涉及用户交互（如搜索、筛选、校验、上传），也需要拆为独立用例，不可仅作为其他用例的预期结果或备注。

**示例：**
- 「车源选择弹层：统一增加搜索」→ 搜索功能独立用例（输入词、结果展示、无结果处理）
- 「支持按字母索引导航」→ 导航功能独立用例

### 规则 5：流程分支必须拆开

当 PRD 描述某个流程后紧跟"如不 X 则 Y"或"若不填写则 Z"等分支描述时，必须拆分为"正常流程"和"分支流程"两条独立用例。

**示例：**
- 「填写检测时间和地点，如不填写关闭，则进入订单结果页」→ 正常填写一条 + 不填写关闭一条
- 「校验通过则提交，校验失败则阻断并提示」→ 通过一条 + 失败一条

### 规则 6：省略式描述不可字面化

当 PRD 使用"与线上一致""同上""流程与 XX 相同"等省略性表述时，不可只记录明确写出的部分，需展开为完整用例，同时记入待澄清问题（因为"线上"的具体行为可能不明确）。

**示例：**
- 「存 600 时打 429tag，补邀约打 tag 流程与线上一致（476）」→ 600→429tag 一条 + 补邀约→476tag 一条 + 660 线索 tag 一条（需待澄清具体 tag 号）

### 规则 7：异常场景不得跳过

当 PRD 描述正常流程后紧跟"XX 为空/错误/异常时，系统应 YY"等异常处理描述时，必须为每个异常场景各生成一条用例，不可只覆盖正常流程。

**示例：**
- 「输入框内手机号为空或位数错误等异常场景时，自动带入登录手机号，并发送验证码」→ 手机号为空一条 + 位数错误一条

## 需求提取清单（中间产物）

**在生成测试用例之前，必须先输出需求提取清单。**

清单生成规则：
1. 逐句扫描 PRD，将每个功能点、规则、校验点、分支逐条列出并编号
2. 每条清单必须标注来源（PRD 中的位置或表格名称）
3. 生成用例后，每条清单必须映射到至少一个用例编号或待澄清问题编号

清单输出格式：
```
需求提取清单：
1. [头图区域] 头图支持静态图片 → TC-001
2. [头图区域] 头图支持动态图片 → TC-002
3. [留资区域] 手机号优先取登录态 → TC-014
4. [留资区域] 手机号一键获取 → TC-015
5. [营销弹层] 挽留弹层 24 小时限制 → TC-044
...
N. [补邀约] 不填写关闭进入订单结果页 → 待澄清 Qx
```

**为什么需要这个清单**：
- 强制 AI 逐条提取，防止信息遗漏
- 提供可追溯的映射关系，方便人工复核
- 清单与用例的交叉检查是最后一道防线

## 标题编写

格式：`{关键条件/场景}` 或 `{操作对象}-{关键条件/场景}`

**关键：括号内的关键区分信息必须保留**，如（方案一/二）、（已登录）、（未勾选）等。这些是区分场景的关键标识，不可省略。

**好的示例：**
- `tc-001-p0：头图-靠左两行样式（方案一/二）`
- `tc-007-p1：未登录（点击入口）`
- `tc-014-p1：登录态自动带入`
- `tc-020-p1：未勾选协议（拦截提交）`

**不好的示例：**
- `tc-001-p0：测试登录功能`（太宽泛）
- `tc-002-p1：输入验证`（没有操作和场景）
- `tc-003-p2：边界值测试`（没有具体操作）

**⚠️ 标题不重复父级：** 写标题时检查最近的 `####` 和 `#####` 章节名，**标题不得以父级章节名中的任何概念词开头**。判定方法：
1. 提取父级 `####` 和 `#####` 章节名中 `-` 分隔的各概念词
2. 若标题以其中任一概念词开头（如 `占优判断-车龄` 以 `占优判断` 开头），去掉该前缀
3. 若标题本身即为某概念词（如 `无总结文案` = 父级 `##### 检测结果-无总结文案` 的概念词），去掉该概念词，只保留核心场景描述
4. 若标题核心操作对象已在父级中出现，直接写 `{关键条件/场景}`
5. 否则写 `{操作对象}-{关键条件/场景}`

示例：
- `#### 固定字段-使用情况` 下：✅ `月均里程正常展示` / ❌ `使用情况-月均里程正常展示`（"使用情况"在父级）
- `##### 使用情况-占优判断` 下：✅ `车龄` /  `占优判断-车龄`（"占优判断"是分组名，不得重复开头）
- `##### 使用情况-总结文案` 下：✅ `当前车占优≥5项` /  `总结文案-当前车占优≥5项`（"总结文案"是分组名）
- `##### 检测结果-无总结文案` 下：✅ `无` / ❌ `无总结文案`（标题即为概念词本身，去掉）
- `#### 本店同款tab` 下：✅ `同车系同商家车源展示`（父级不含"车源"，保留操作对象）

## 前置条件编写

- 前置条件与测试动作合并为一行：`{前置条件}，{测试动作}`
- 只列出**该用例特有的前置条件**，模块级公共前置在模块开头统一列出
- 使用「状态描述」句式，如「用户已注册账号 test001」「订单状态为待支付」
- 精简描述核心条件，不使用「网络正常」「浏览器已打开」等通用描述
- 无前置条件时，直接写动作

---

## 测试步骤编写

- 合并入条件+动作行，不单独成行
- 格式：`{条件}，{动作1}，{动作2}，{动作3}`
- 每步描述一个用户操作或系统动作，精简核心操作
- 步骤数量由 AI 自行决定，保证可读性即可
- 若 PRD 中包含计算公式或业务规则，在对应步骤中直接写明具体数值或公式

---

## 预期结果编写

- 逐条展开为子节点，不编号
- 每条一个独立校验点
- 必须可判定，不使用"应该""可能""正常显示"等模糊词
- 若需求天然描述同一动作下的连续结果，可在同一条件下以子节点逐条列出
- **【图片:xxx】紧跟在对应的预期结果行尾**，其他预期结果不加

---

## 来源标注

每条用例通过前置条件行尾的标注区分来源：

- **PRD原文**：需求文档中明确写到的场景，**默认不标注**
- **主动补充**：PRD 中未写到，但根据测试经验应覆盖的场景，写 `【主动补充】`

这样团队可以清楚区分哪些是需求明确要求的，哪些是 QA 主动扩展的。

## 自动化标记

通过条件+动作行尾的标注标记：

- **有才写**：`【自动化:是】`
- **不写**：适合人工执行的用例（如页面布局、颜色、文案、用户体验）

| 优先级 | 定义 | 典型场景 |
|-------|------|---------|

## D9-D12 用例生成模板

### D9 第三方交互

适用于 PRD 中出现"跳转 xx"、"唤起 xx"、"打开 xx"等外部应用交互描述。

**用例模板：**
```markdown
- tc-XXX-p1：{功能}-{第三方应用}-{结果}
  - {前置条件}，{触发交互动作}
    - 正确跳转/唤起目标应用
    - 参数传递正确（如地址坐标、订单 ID）
    - 第三方应用操作完成后返回 APP，状态刷新正确
    - 第三方应用未安装/跳转失败时，提示错误并留在当前页
```

**拆分规则：**
- 正常跳转/唤起：1 条
- 跳转失败/未安装：1 条
- 返回后状态刷新：1 条（如从易签宝签约返回后状态变更）

---

### D10 数据展示边界

适用于 PRD 中出现"展示 xx"且有数据来源的场景。

**用例模板：**
```markdown
- tc-XXX-p1：{数据字段}-{空态/超长/异常}
  - {接口返回异常数据}，{进入页面}
    - 页面不崩溃，无白屏
    - 按兜底逻辑展示（如"--"、隐藏该字段、或展示默认文案）
    - 其他正常数据不受影响，正确展示
```

**拆分规则：**
- 空态（null/空字符串）：1 条
- 超长（文案/地址/名称超出限制）：1 条
- 异常格式（类型错误/关联数据缺失）：1 条

---

### D11 关键分支（顺序）

适用于 PRD 中出现"优先"、"如没有则"、"反之"等多条件互斥描述。

**用例模板：**
```markdown
- tc-XXX-p0：{功能}-{条件 A 优先}
  - {满足条件 A}，{触发动作}
    - 按条件 A 路径执行
- tc-XXX-p0：{功能}-{条件 B 降级}
  - {不满足条件 A 但满足条件 B}，{触发动作}
    - 按条件 B 路径执行
    - 不执行条件 A 路径
```

**拆分规则：**
- 每个条件路径各 1 条
- 条件互斥时，额外增加 1 条"同时满足多条件"用例，验证优先级是否正确

---

### D12 触区与机型

适用于 PRD 中出现可点击元素或适配要求的场景。

**用例模板：**
```markdown
- tc-XXX-p2：{按钮/元素}-{边缘点击}
  - 点击按钮边缘/极小区域
    - 按钮响应正常，功能可触发
- tc-XXX-p3：{页面}-{横竖屏切换}
  - 进行横竖屏切换
    - 布局自适应，元素无重叠截断
    - 数据保留，状态不丢失
```

**拆分规则：**
- 按钮热区：1 条
- 横竖屏切换：1 条（覆盖所有含交互的页面）
- 长文案适配：1 条（针对有最大行数限制的字段）

## 埋点用例生成规则

### 适用范围

仅当 PRD 中包含埋点/数据上报需求时，本规则生效。

### 核心规则

| 规则 | 内容 |
|-----|------|
| **优先级** | 埋点用例统一为 `tc-p3` |
| **合并规则** | 同一埋点事件的所有参数分支**合并为一条用例**，不拆分 |
| **标题** | 用事件中文名或功能描述，如 `埋点-页面展现`、`埋点-按钮点击` |
| **输出位置** | 统一放在文末 `## 四、埋点测试` 独立模块中，不归属到单一功能点 |
| **严格限制** | **仅使用需求明确信息**，不扩展、不推测、不概括、不简化、不改写 |

### 用例模板

```markdown
- tc-XXX-p3：埋点-{事件中文名}
  - 进入{页面名称}，触发{事件类型}埋点
    - 事件名：{用户输入中明确的事件 ID}
    - 触发时机：{用户输入中明确的触发时机}
    - 上报次数：{用户输入中明确的上报次数}
    - 关键参数：
      - {用户输入中明确的参数 1}：{参数说明}
      - {用户输入中明确的参数 2}：{参数说明}
      - ...
    - 参数枚举：
      - platform：10=pc、20=m、30=ios、40=android、50=nq_ios、60=nq_android
      - pos：1=头图、2=滚动条、3=卖车说明
```

### 参数枚举格式规范

格式：`参数名=值1/值2/值3：值1=含义1、值2=含义2、值3=含义3`

- 所有枚举值必须附带中文含义
- 不得省略、合并或改写枚举含义
- 多个枚举参数分行列出

### 关键约束

- 禁止编造需求中未提及的埋点事件或参数
- 禁止概括、简化需求中的参数定义与枚举含义
- 所有参数、枚举、触发时机必须原样保留 PRD 中的描述
- 如果 PRD 中定义了多个埋点事件，每个事件生成一条用例
