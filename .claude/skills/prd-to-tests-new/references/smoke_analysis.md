# 三方多维度分析

## 目标
对 PRD 需求进行深度多角色审查，输出结构化的三方分析报告。

## 适用场景
- 用户明确要求"三方分析"、"多维度分析"、"方案评审"
- 生成冒烟用例前的必经分析步骤
- 需要独立输出分析报告的场景

## 角色定义

### 产品专家 (The Visionary)
关注"做正确的事"。追求业务逻辑的严密性、用户体验的无缝衔接以及商业价值的最大化。

分析维度：
- 核心业务逻辑链是否完整
- 用户场景覆盖是否充分（正向场景、异常场景、边界场景）
- 功能边界和优先级是否清晰
- 商业价值和 ROI 是否合理
- 需求描述是否存在歧义、矛盾或遗漏

### 架构师 (The Builder)
关注"正确地做事"。追求系统的高性能、高伸缩性、安全性和技术方案的优雅。

分析维度：
- 技术选型是否匹配需求规模
- 数据流向和状态管理是否清晰
- 是否存在性能瓶颈或单点故障
- 扩展性、安全性和可维护性
- 接口定义是否完整（入参、出参、错误码）
- 数据一致性保障机制

### 测试专家 (The Gatekeeper)
负责"把事做对"。彻头彻尾的怀疑论者，专注于寻找漏洞、边界情况和系统崩溃的可能。

分析维度：
- 输入验证和边界条件
- 并发/竞态条件
- 异常处理和容错
- 安全漏洞和数据一致性
- 回归影响范围
- 可测试性评估

## 执行流程

### 第一阶段：独立分析

三个专家分别给出专业意见，输出格式：

```
## 产品专家分析
### 业务逻辑链
{梳理核心业务流程，标注断点和缺失环节}

### 用户场景覆盖
{列出已覆盖场景和遗漏场景}

### 功能边界与优先级
{明确各功能边界，标注模糊地带}

### 需求缺陷
{列出矛盾、歧义、遗漏、过度设计}

## 架构师分析
### 技术架构评估
{数据流向、状态管理、技术选型}

### 性能与扩展性
{瓶颈点、扩容方案、并发处理}

### 安全与稳定性
{安全风险、单点故障、降级方案}

### 接口完整性
{缺失接口、参数不完整、错误码缺失}

## 测试专家分析
### 核心测试要点
{必须验证的功能点和场景}

### 风险点清单
{高风险功能、易出错环节}

### 边界情况
{极端输入、极限状态、边界条件}

### 安全隐患
{越权、注入、越界访问、数据泄露}
```

### 第二阶段：红蓝对抗

进入对抗模式，必须明确指出真实问题：

```
## 质询环节

### QA → 产品
{挑战业务逻辑中的歧义、被滥用可能、用户误解风险}
- 问题 1：...
- 问题 2：...

### QA → 架构
{质疑高并发/宕机/极端情况下的系统表现}
- 问题 1：...
- 问题 2：...

### 架构 → 产品
{评估技术实现成本、指出过度设计或不可行的环节}
- 问题 1：...
- 问题 2：...
```

**约束**：
- 每个对抗方向至少提出 2 个具体问题
- 禁止模棱两可——发现风险必须明确说"这里会挂掉"或"这里逻辑不通"
- 语言风格：专业、直接、有技术深度

### 第三阶段：结论汇总

基于独立分析和对抗结果，输出：

```
## 三方结论

### 关键风险（必须解决）
| 序号 | 风险描述 | 涉及角色 | 严重程度 | 建议措施 |

### 架构建议
{技术实现层面的优化建议}

### 产品建议
{需求完善和边界补充建议}

### 测试重点
{后续测试必须重点关注的方向}

### 冒烟测试范围建议
{建议纳入冒烟测试的核心功能点}
```

## 输出文件

分析报告保存为 `{项目名称}_三方分析.md`，放在与最终测试用例相同的输出目录。
