# Step 2: 功能点拆分

## 目标
将 PRD 中的需求拆解为可独立测试的功能点，**仅关注 P0 级别核心功能**，为后续冒烟用例生成提供输入。

## 必须输出清单

执行本步骤前，必须逐项声明：

- [ ] 已列出所有功能模块及其层级关系
- [ ] 已识别所有 P0 功能点并分配唯一编号
- [ ] 已标注 P0 功能点之间的依赖关系
- [ ] 已识别新增/变更/删除的 P0 功能
- [ ] P0 功能点已覆盖核心业务流程的完整路径

## 执行步骤

### 2.1 功能模块拆分

按 PRD 的章节结构，将需求拆分为功能模块树：

```
产品/项目
├── 模块 A
│   ├── 功能点 A.1
│   ├── 功能点 A.2
│   └── 功能点 A.3
├── 模块 B
│   ├── 功能点 B.1
│   └── 功能点 B.2
└── 模块 C
    └── 功能点 C.1
```

**仅拆分 P0 功能点**。对于 P1/P2/P3 功能点，只需在模块树中标注名称和优先级，不做详细拆分。

每个 P0 功能点必须标注：
- **编号**：如 `F-A-01`、`F-B-02`
- **名称**：简洁描述功能
- **优先级**：P0
- **类型**：新增 / 修改 / 删除

#### 对抗性验证（每个功能点拆分后必须执行）

对每一个功能点，必须自问以下问题，并将答案记录在功能点备注中：
- **异常路径**：该功能的正常流程之外，用户可能以什么方式触发异常？
- **边界条件**：什么极端输入/状态会导致功能失效或异常行为？
- **并发/竞态**：多用户同时操作时，该功能的数据一致性如何保障？
- **失败回滚**：操作失败后，系统状态是否回滚到安全状态？残留数据如何处理？
- **权限越界**：是否存在低权限用户可能访问高权限功能的路径？

禁止只拆分 Happy Path。如果一个功能点无法回答上述任一问题，必须标记为「待补充分析」，并在最终文档中列入风险项。

### 2.2 业务流程拆分

对每个涉及流程的 P0 功能点，提取其核心流程步骤（仅正常路径）：

- **入口条件**：什么情况下可以进入该流程
- **正常路径**：用户按预期操作完成的步骤序列（步骤不超过 5 步）
- **退出条件**：流程正常结束的状态

**注意**：冒烟用例不覆盖分支路径和异常退出，这些信息在三方分析报告中记录即可。

### 2.3 数据变更点识别

标记每个功能点涉及的数据操作：

- **创建**：新增记录 / 实体
- **读取**：查询 / 展示 / 检索
- **更新**：修改 / 编辑 / 状态变更
- **删除**：软删除 / 硬删除 / 归档
- **导入/导出**：批量数据操作

### 2.4 关联影响分析

识别功能变更对其他模块的影响：

- **直接依赖**：本功能直接调用的其他模块
- **间接依赖**：通过中间层影响的其他模块
- **共享数据**：与本功能共享数据表 / 缓存的其他模块
- **共享权限**：与本功能共用权限的角色

### 2.5 功能点优先级分配

- **P0（核心阻断）**：主流程、核心业务、支付/安全相关 —— **本步骤只详细拆分此类功能点**
- **P1（重要功能）**：主要业务场景、高频操作 —— 仅标注，不详细拆分
- **P2（次要功能）**：低频操作、辅助功能、管理后台 —— 仅标注，不详细拆分
- **P3（体验优化）**：UI 细节、交互体验、提示文案 —— 仅标注，不详细拆分

### 2.6 问题映射与覆盖验证

将三方分析报告中汇总的所有问题，逐一映射到本步骤拆分的 P0 功能点上：

```
## 问题映射表
| 问题序号 | 问题描述 | 映射功能点编号 | 映射功能点名称 | 覆盖状态 |
```

**覆盖状态定义：**
- **已覆盖**：该问题已在某个 P0 功能点的拆分中被识别，并将在后续冒烟用例中体现
- **未覆盖**：该问题尚未找到对应 P0 功能点，需要补充拆分或标记为全局问题
- **不适用**：该问题属于全局性/非功能性问题，不映射到具体功能点

**验证约束：**
- 所有严重程度为「阻断」或「高」的问题，覆盖状态必须为「已覆盖」或「不适用」
- 任何标记为「未覆盖」的严重问题，必须回溯补充 P0 功能点拆分
- 全局性问题（如性能基线、安全合规）在冒烟用例中单独标记为验收条件

本步骤的输出是 Step 4（冒烟用例生成）的核心输入：P0 功能点树 + 问题映射表共同决定冒烟测试覆盖的完整性。
