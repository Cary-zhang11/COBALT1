"需求数" 轻量去重方案

放弃全文本 MD5，改用更轻量的识别方式

A

按上传文件名去重（推荐）

从 inputFiles 中提取文件名，去掉上传时间戳前缀，归一化后去重。如 "1780581436572-卖车页面改版.docx" → "卖车页面改版.docx"。同一文档多次上传，文件名相同即算 1 个需求。

B

按 input 前 100 字符哈希去重

只取 input 的前 100 个字符做哈希。PRD 的开头通常是标题/概述，足够区分不同文档。比全文字段轻很多。

C

新增 digest 字段，创建任务时预计算

在 task 表加一个 inputDigest 字段，创建任务时就对 input 前 N 字符取哈希存下来。查询时直接 COUNT(DISTINCT inputDigest)，零额外开销。

对比

A 文件名 B 前100字 C 预计算
查询性能 轻量 中等 最轻
准确度 高（同文档同文件名） 较高 高
改造量 无需改表 无需改表 需加字段+迁移
缺点 依赖用户上传文件;
纯粘贴文本的需求区分不了		 前100字相同但实际是不同
需求的低概率误判		 需迁移历史数据补算
推荐方案 A（文件名去重），理由：
  • 零 schema 变更，不读 input 全文，查询只需解析 inputFiles 数组
  • 实际使用中绝大多数需求都来自文件上传（看 uploads 目录，文件命名已有规律）
  • 文件名提取逻辑简单：去掉时间戳前缀，保留原名
  • 对于粘贴文本的需求（无文件），可回退用 input 前 50 字符作为标识
